## Clarifications

### Session 2026-03-11

- Q: Who is responsible for producing the topologically sorted output — the AI or the system? → A: The AI outputs nodes in their final order, respecting all prerequisite and elective selection rules. The system validates the sequence and treats any ordering violation as a generation failure.
- Q: Who or what surfaces the retry trigger to the student? → A: Both — the in-app error notification carries a retry call-to-action, AND the Skill Tree (Feature 004) exposes a retry action whenever the roadmap has no `acceptedAt` (i.e., is in a failed/retryable state).
- Q: Should `skills` be deduplicated across the whole roadmap, or scoped independently per node? → A: Each node's `skills` is determined by feature 003. Deduplication is a presentation concern owned by Feature 004. *(Superseded by Session 2026-04-07 — skill is now the primary node identity, not a field on the node.)*
- Q4 dropped — automatic upgrade of low-personalisation roadmap when profile is enriched is a frontend/rendering concern; not in scope for this backend feature.
- Decision: All generated roadmaps (initial and re-generation) require explicit student acceptance before commit. The pre-acceptance state (RoadmapPreview) remains transient and not persisted in the main collection. A user may hold multiple roadmap documents, but exactly one roadmap is primary at any time.
- Decision: Re-generation triggered uses the student's existing accepted roadmap as additional AI context. The previous roadmap remains active until the student accepts the new preview; it is preserved unchanged if the student rejects the preview.
- Q: Where does the RoadmapPreview live and does it expire? → A: The preview is held in-memory on the background worker only. It does not survive a worker restart and is not readable cross-session. A worker restart while a preview is pending is treated as a generation failure; the retry mechanism becomes available.
- Q: If no accepted roadmap exists when triggering re-generation, what happens? → A: Re-generation proceeds as a fresh initial generation — StudentProfile and DAG are the only inputs; no base roadmap context is provided to the AI. This is not an error.
- Decision (canonical ownership): Feature 009 is the sole owner of roadmap lifecycle/state-transition rules. All other features consume roadmap data via 009 API/service contract only.

### Session 2026-04-07

- Q: What is the primary identity of a RoadmapNode — a course or a skill? → A: Skill is the primary identity. Each node represents a skill; course references are stored in a `relatedCourses` field inside the node.
- Q: How is the ordering of skill nodes in the roadmap determined? → A: Ordering is determined jointly — roadmap templates stored in the database provide a base order, and the AI resolves final ordering.
- Q: What is a roadmap template? → A: A roadmap template is a full roadmap with low personalisation. It represents the canonical, generic skill sequence for a major/career track and serves as the base structure the AI uses when generating a personalised roadmap.
- Q: Who creates roadmap templates and where are they stored? → A: Templates are hardcoded by another feature as static JSON files in source code (not a MongoDB collection). Feature 009 reads them from the bundled JSON at generation time.
- Q: When a generated roadmap matches the template exactly (low-personalisation), does it bypass the acceptance lifecycle? → A: No. Every generated roadmap — including low-personalisation output — always goes through the standard preview → acceptance lifecycle. No special-casing for template-identical output.
- Decision: The roadmap has two layers of nodes — modelled after the roadmap.sh topic/subtopic pattern. **Topic nodes** (`nodeType: topic`) form the sequential core main line, each foundational to the career goal. **Subtopic nodes** (`nodeType: subtopic`) are specific tools/technologies branching off a topic, linked via `parentNodeId`. Node progress state is NOT embedded in the node. Progress tracking is owned by Feature 009 via the `roadmap_progress` collection — see `RoadmapProgress` in Key Entities.

### Session 2026-04-08

- Q: Do CourseUnit documents already carry a `skills` array field as persisted data? → A: Yes. CourseUnit documents carry a pre-seeded `skills` array (seeded as part of Feature 002/003). Skills are not generated by the AI at roadmap generation time.
- Q: How precisely does the system use the roadmap template to determine node ordering for the collected skills? → A: The template defines the canonical skill sequence. Each collected skill is mapped to its position in the template; template-matched skills are ordered by their template position. Skills absent from the template have their insertion position and node type (`topic` or `subtopic`) determined by the AI. *(Refines Session 2026-04-07 ordering answer.)*
- Q: Does skill deduplication remain Feature 004's responsibility after generation? → A: No. Feature 009 owns deduplication at generation time — the system collects `skills` arrays from all selected CourseUnit documents and deduplicates them to produce a unified skills list before building nodes. Feature 004 is not responsible for deduplication.
- Decision: Node progress `state` is removed from `RoadmapNode`. Progress tracking for nodes is owned by Feature 009 in the `roadmap_progress` collection (`RoadmapProgress` entity); Feature 009 does not embed or initialise per-node progress state directly on the `Roadmap` document.
- Decision: `errorMessage` is removed from the Roadmap document. Failure context is surfaced through the notification system (FR-027) and is not stored on the roadmap document itself.
- Decision: `status` field is removed from the Roadmap document. Acceptance is indicated by the presence of an `acceptedAt` timestamp; a Roadmap document without `acceptedAt` is in a failed/retryable state. No other persisted status values exist.

### Session 2026-04-09

- Q: Should a completed course appear in `relatedCourses` if it delivers a skill that is still present as a node? → A: No. `relatedCourses` only lists courses from the selected (non-completed) set. Visual treatment of completion state (e.g., strikethrough) is a Feature 004 rendering concern, out of scope for Feature 009.
- Q: For skills absent from the roadmap template, how is their inclusion and placement determined? → A: Two-step. First, the AI evaluates whether the skill is relevant to the student's career goal — skills judged not relevant are excluded and do not become nodes. Second, skills judged relevant are inserted at a position in the sequence adjacent to the nodes that share the same `relatedCourses` (i.e., near other skills delivered by the same course(s)). Prerequisite ordering constraints still apply to the final sequence regardless of placement.
- Q: What `nodeType` may an off-template skill node have? → A: Off-template nodes are always `subtopic`. They must be attached via `parentNodeId` to an existing template-matched topic node in the same `relatedCourses` adjacency group. An off-template skill that cannot be attached to any existing topic node in its group MUST be excluded — the system must never create a new topic node for an off-template skill.
- Q: Should SC-001 and SC-003 be rewritten to use skill-node language? → A: Yes. Success criteria must be testable against the actual output shape — skill nodes, not courses.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Generate Personalised Roadmap from Full Profile (Priority: P1)

When a student submits their full onboarding profile (including career goal, completed courses, and other optional fields), the system asynchronously generates a personalised learning roadmap. The system selects a career-targeted subset of courses — all required prerequisite courses plus only the electives the AI determines are most relevant to the student's stated role and company type — then collects and deduplicates the skills from those courses to produce an ordered list of skill nodes. Each skill node carries the course(s) that deliver it, a plain-language reason explaining why this skill matters for the student's specific career goal, and a `resources` field (always `[]` at generation time). Upon completion, the student is presented with a roadmap preview; the roadmap is committed as their active roadmap only after they explicitly accept it.

**Why this priority**: This is the core value delivery of the entire system. Without a generated roadmap, UETCompass provides no learning guidance. All downstream features (Skill Tree, Resource Curation) depend on this output existing.

**Independent Test**: Can be fully tested by triggering generation with a complete StudentProfile (all fields filled), then verifying the stored Roadmap document contains: only skill nodes derived from career-relevant courses, ordered consistently with prerequisite constraints, no skills from completed-only courses appearing as actionable nodes, and every node having a non-empty `skillName`, a non-empty `reason`, and `resources: []`.

**Acceptance Scenarios**:

1. **Given** a student has submitted a full profile with major, completedCourseIds, and a career goal, **When** the profile submission event fires, **Then** the system accepts it and begins asynchronous roadmap generation without blocking any other student activity.
2. **Given** generation is in progress, **When** the AI selects courses, **Then** all required courses that are direct or transitive prerequisites of career-relevant courses are included, and only career-relevant electives are included.
3. **Given** the student has completed courses, **When** the roadmap is assembled, **Then** completed courses do not appear as actionable roadmap nodes, but their prerequisite relationships are used to determine which subsequent nodes are already unlocked.
4. **Given** the course selection is complete, **When** the roadmap nodes are ordered, **Then** every node appears after all of its prerequisite nodes in the sequence, with no exceptions.
5. **Given** every course is selected and ordered, **When** the system builds each skill node, **Then** each node's `skillName` is populated from the course's pre-seeded `skills` array, the node carries a `reason`, and `resources: []`.
6. **Given** generation completes successfully, **When** the AI output is validated, **Then** a roadmap preview is prepared and the student receives an in-app notification that their roadmap is ready for review.
7. **Given** the student reviews the roadmap payload, **When** the student accepts it through the 009 acceptance contract, **Then** the roadmap is committed as a Roadmap document and may become primary according to primary-selection rules.
8. **Given** the student reviews the roadmap preview, **When** the student rejects it, **Then** the preview is discarded, any existing roadmap remains unchanged, and the retry mechanism becomes available.

### User Story 2 - Generate Generic Roadmap from Minimal Profile (Priority: P2)

A student submits their onboarding with only the required major field filled in and no career goal provided. The system generates a generic roadmap whose skill nodes are sourced from the pre-seeded `skills` arrays of the core required courses for that major, ordered consistently with prerequisite constraints. The roadmap is explicitly flagged as low-personalisation so the downstream Skill Tree can surface a notice prompting the student to enrich their profile.

**Why this priority**: Students who submit minimal profiles must not be left without a roadmap. A generic fallback ensures the system always delivers value while communicating clearly that personalisation was limited.

**Independent Test**: Can be fully tested by triggering generation with a StudentProfile containing only a major (all optional fields empty), then verifying the stored Roadmap document contains skill nodes derived from all required courses for that major, ordered consistently with prerequisite constraints, with a low-personalisation flag set, and every node having a non-empty `skillName` and `resources: []`.

**Acceptance Scenarios**:

1. **Given** a student has submitted a profile with only a major and no career goal, **When** generation is triggered, **Then** the system detects the absence of career goal data and routes generation through the generic pathway.
2. **Given** generic generation mode is active, **When** the AI selects courses, **Then** all required courses for the student's major are included; AI-evaluated off-template elective skills are excluded (no AI call is made in this mode) — elective skills that match template positions are included as template-matched nodes.
3. **Given** courses are selected in generic mode, **When** the system builds nodes, **Then** each `skillName` is sourced directly from the pre-seeded `skills` arrays of the selected required courses — no AI-driven skill customisation or role-specific filtering is applied.
4. **Given** generic generation completes, **When** the roadmap preview is prepared, **Then** it carries a low-personalisation flag.
5. **Given** the roadmap preview is ready, **When** the student receives their notification, **Then** the notification includes an indication that personalisation quality is limited.
6. **Given** the student reviews the generic roadmap payload, **When** the student accepts it, **Then** the roadmap is committed carrying the low-personalisation flag and managed under the same primary-selection rules.

### User Story 3 - Retry Roadmap Generation After Failure (Priority: P3)

Roadmap generation fails due to an AI service error or timeout. The system stores the failure state and the student receives an error notification. The student can trigger a retry without resubmitting their profile. On retry, generation runs through the same lifecycle as the initial attempt and produces a complete Roadmap document that replaces any previous (failed) state.

**Why this priority**: Generation failures are anticipated and the retry path is the recovery mechanism. Without it, a failed generation permanently leaves the student without a roadmap.

**Independent Test**: Can be fully tested by simulating a generation failure, confirming the error state is stored and the student is notified, then triggering a retry and confirming a complete Roadmap is produced and replaces the failed state.

**Acceptance Scenarios**:

1. **Given** generation encounters a failure (AI service error, timeout, or malformed AI output), **When** the failure is detected, **Then** the system persists a Roadmap document without `acceptedAt` (marking it failed/retryable) without corrupting the student's profile.
2. **Given** a failed generation state is stored, **When** the system finishes error handling, **Then** the student receives an in-app error notification.
3. **Given** a failed Roadmap state exists, **When** the student triggers a retry, **Then** generation re-reads the existing StudentProfile and re-runs the full generation lifecycle.
4. **Given** a retry generation completes successfully, **When** the accepted roadmap is committed, **Then** canonical transition rules are applied and stale failure state is not exposed as the latest accepted version.
5. **Given** the student has not resubmitted their profile, **When** they initiate a retry, **Then** the system uses the same StudentProfile as the original attempt.

### User Story 4 - Re-generate Roadmap on Career Goal Update (Priority: P3)

After a student updates their career goal in Account Settings, the system re-generates the roadmap using the student's existing accepted roadmap as a base alongside the updated profile — previously approved skill selections inform the new output without constraining it. Re-generation runs asynchronously. On completion, the student is presented with a preview of the updated roadmap. The previous roadmap remains the student's active roadmap until the student explicitly accepts the preview. If the student rejects the preview, the previous roadmap is preserved unchanged.

**Why this priority**: Without re-generation, career goal updates in Account Settings have no effect on the student's roadmap, rendering that feature's personalisation update meaningless.

**Independent Test**: Can be fully tested by updating a student's career goal, triggering re-generation, confirming the preview builds on the existing roadmap and reflects the new career goal, accepting it, and verifying the new roadmap supersedes the previous one. Separately verified by rejecting the preview and confirming the previous roadmap remains intact and unchanged.

**Acceptance Scenarios**:

1. **Given** a student's career goal has been updated, **When** re-generation is triggered, **Then** it runs asynchronously without blocking the student, and the existing accepted roadmap is provided to the AI as additional context.
2. **Given** re-generation is in progress, **When** the AI generates the updated roadmap, **Then** it uses the updated career goal from the current StudentProfile and the existing accepted roadmap as a base; the previous skill selections inform but do not constrain the new output.
3. **Given** re-generation completes successfully, **When** the roadmap preview is ready, **Then** the student receives an in-app notification that their updated roadmap is ready for review.
4. **Given** the student reviews the updated roadmap payload, **When** the student accepts it, **Then** the accepted roadmap is committed under canonical transition rules and primary assignment is consistent.
5. **Given** the student reviews the updated roadmap preview, **When** the student rejects it, **Then** the preview is discarded and the previous roadmap remains the student's active roadmap unchanged.
6. **Given** re-generation fails, **When** the failure is detected, **Then** the same retry mechanism is available as for initial generation failure, and the previous roadmap remains in the database unchanged.

### Edge Cases

- **All courses already completed**: If the student's `completedCourseIds` covers all (or nearly all) required courses for their major and career-relevant electives, the resulting actionable roadmap may be empty or near-empty. The system MUST store this as a valid result — an empty or minimal roadmap is a correct output, not a failure.
- **AI returns malformed or incomplete output**: If the AI's response cannot be parsed into a valid Roadmap document, the generation is treated as a failure: the error state is stored, and the retry mechanism becomes available.
- **Generation triggered while another is in progress**: If a retry or repersonalization trigger fires while generation is already running for the same student, the new trigger MUST be queued or debounced — duplicate concurrent generations for the same student MUST NOT occur.
- **Elective course pool is empty for a given major**: If a major has no elective courses in the DAG seed data, the AI must generate a valid roadmap from required courses only, without treating this as an error.
- (Removed: repersonalizationPending fires immediately after profile submission)
- **Prerequisites form a cycle** (data integrity guard): If the CourseUnit DAG unexpectedly contains a cycle (a data integrity violation from Feature 002), generation MUST fail with a descriptive error rather than entering an infinite loop.
- **Career goal is free-text with no recognizable role**: If the career goal is a fully custom free-text value with no predefined mapping, the system selects the generic `careerTrack: null` template (since the free-text value will not match any template `careerTrack`); the AI must still attempt to reason about the free-text value when evaluating off-template skills and MUST NOT fall back to the low-personalisation pathway (which skips the AI call entirely) unless the career goal field is wholly absent.
- **Student rejects initial roadmap preview**: If a student has no active roadmap and rejects the first generated preview, the preview is discarded, the student is left without an active roadmap, and the retry mechanism becomes available so they can request a new generation attempt.
- **Student rejects re-generation preview**: The existing accepted roadmap remains the student's active roadmap, completely unchanged. The preview is discarded. The student may trigger re-generation again at any time by updating their career goal in Account Settings.
- (Removed: repersonalizationPending triggers with no accepted roadmap)
- **Worker restart while preview is pending**: If the background worker restarts after generation has completed but before the student has accepted or rejected the preview, the in-memory preview is lost. This MUST be treated as a generation failure: a Roadmap document without `acceptedAt` is persisted (marking it failed/retryable), the student is notified, and the retry mechanism becomes available. The previous accepted roadmap (if any) remains unchanged.

## Requirements *(mandatory)*

### Functional Requirements

**Generation Trigger and Lifecycle**

- **FR-001**: The system MUST initiate roadmap generation asynchronously when a student's onboarding profile submission event fires (as produced by Feature 001).
- **FR-002**: The system MUST support re-generation, following the same generation lifecycle as initial generation.
- **FR-003**: Generation MUST run fully asynchronously and MUST NOT block the student's use of any other part of the system.
- **FR-004**: If a generation trigger fires for a student who already has a generation in progress, the system MUST NOT launch a duplicate concurrent generation for that student.

**Input Retrieval**

- **FR-005**: Before generation, the system MUST retrieve the student's complete StudentProfile, including: `major`, `completedCourseIds`, `careerGoal.role`, `careerGoal.companyType`, `graduationTimeline`, and `personalAspirations`.
- **FR-006**: Before generation, the system MUST retrieve the full CourseUnit DAG for the student's major, as seeded by Feature 002, including all course codes, names, credits, types (`required` / `elective`), prerequisite arrays, and `skills` arrays.

**Off-Template Skill Evaluation**

- **FR-007**: The system MUST execute the following generation pipeline: (1) retrieve all courses for the student's major from the CourseUnit DAG; (2) collect the `skills` arrays from all non-completed CourseUnit documents for the major, build a reverse map (skillName → CourseUnit[]), and deduplicate to produce a unified skills list; (3) load the roadmap template by matching `{ careerTrack: profile.careerGoal.role }` — if `careerGoal.role` is absent or does not match any known `careerTrack`, fall back to the template with `{ careerTrack: null }` (generic template); compare the deduplicated skills list against the loaded template — skills present in the template are ordered by their template position and inherit their `nodeType` (`topic` or `subtopic`), `parentNodeId`, `reason`, and `resources` from the template (defaulting to `[]` if absent or null), with `relatedCourses` populated from the reverse map; (4) for skills absent from the template, the AI evaluates each for career-goal relevance, receiving the student's profile and Program description as context (per FR-008) — skills judged not relevant MUST be excluded; (5) off-template skills approved by the AI MUST be assigned `nodeType: subtopic` and mapped to the template-matched topic node whose `relatedCourses` shares the greatest number of course codes with the off-template skill's own `relatedCourses` (per FR-009) — if no topic node shares any courses the skill MUST be excluded; (6) enrich each resulting skill node (per FR-013, FR-015, FR-017).
- **FR-008**: The AI MUST evaluate each off-template skill for relevance to the student's stated career goal. The evaluation input MUST include the student's profile (`major`, `careerGoal`, `graduationTimeline`, `personalAspirations`) and the Program description. For each approved skill the AI MUST return both the `skillName` and a `reason` explaining why it is relevant to the student's career goal. Skills judged not relevant MUST be excluded and MUST NOT become nodes. If no career goal is provided, all off-template skills MUST be excluded without making an AI call.
- **FR-009**: Off-template skills approved by the AI MUST always be assigned `nodeType: subtopic`. The system MUST compute the course-code overlap between the off-template skill's `relatedCourses` and the `relatedCourses` of every template-matched topic node, and assign `parentNodeId` to the topic node with the greatest overlap count. If the maximum overlap count is zero (no shared courses with any topic node), the skill MUST be excluded.
- **FR-010**: Courses present in `completedCourseIds` MUST NOT appear as actionable roadmap nodes in the output.
- **FR-011**: Completed courses MUST be used as satisfied prerequisite anchors — the system MUST treat them as unlocked when determining which subsequent nodes in the DAG are now accessible.

**Node Ordering**

- **FR-012**: Roadmap nodes MUST be ordered as follows: skills present in the roadmap template are positioned by their template order; off-template skills that pass the career-relevance evaluation (FR-007 step 4) are inserted adjacent to their mapped parent topic node (FR-007 step 5, FR-009). The system MUST validate the final node sequence — if any node appears before a node it depends on directly or transitively, the system MUST treat it as a generation failure and invoke the standard failure-handling path (store error state, notify student, allow retry).

**Node Enrichment**

- **FR-013**: Each roadmap node MUST represent a single skill as its primary identity. The node MUST carry a `skillName` field sourced from the pre-seeded `skills` arrays of the CourseUnit documents for the major (non-empty string) and a `relatedCourses` field listing every non-completed CourseUnit whose `skills` array contains that skill name — each entry populated as `{ courseCode, courseName, credits }` from the source CourseUnit document. Completed courses MUST NOT appear in `relatedCourses` even if they deliver the same skill. The system MUST build a reverse map (skillName → CourseUnit[]) during step 2 of the generation pipeline (FR-007), operating over all non-completed CourseUnit documents for the major, and use it to derive `relatedCourses` for each node. The system MUST deduplicate skills across all courses at generation time — each unique skill name from the unified skills list produces exactly one node. Feature 004 is not responsible for skill deduplication.
- **FR-015**: Each roadmap node MUST include a `reason` field: a plain-language explanation of why this skill is included in the roadmap and how it contributes to the student's career goal. For template-matched nodes, `reason` MUST be inherited directly from the template's `TemplateNode.reason` field. For off-template nodes, `reason` MUST be the value returned by the AI during the off-template evaluation call (FR-008) — no separate enrichment call is made for those nodes.
- **FR-016**: Each roadmap node MUST carry a stable `nodeId`. For template-matched nodes, `nodeId` MUST be inherited from the template's `TemplateNode.id` field. For off-template nodes, `nodeId` MUST be generated as a kebab-case slug of the `skillName` (e.g. `"Git Flow"` → `"git-flow"`). Because `skillName` is deduplicated within a roadmap, the slug is guaranteed unique within a single roadmap document without requiring a UUID. `nodeId` MUST remain stable across re-generations for the same skill to preserve Feature 004's node references.
- **FR-017**: Each roadmap node MUST include a `resources` field. For template-matched nodes, `resources` is inherited from the template's `TemplateNode.resources`; if the template node has no `resources` value or the value is null, the system MUST default to `[]`. For off-template nodes, `resources` MUST always be `[]`. The field MUST exist in the schema, MUST NOT be omitted, and MUST NOT be null at generation time.

**Low-Personalisation (Minimal Profile) Pathway**

- **FR-018**: If the student's profile contains no career goal (both `careerGoal.role` and `careerGoal.companyType` are absent or empty), the system MUST generate a generic roadmap covering the required courses of the student's major in valid prerequisite order.
- **FR-019**: In the low-personalisation pathway, the same skill collection and deduplication pipeline (FR-007 steps 2–3) applies — skills are sourced from the pre-seeded `skills` arrays of all non-completed courses for the major. Off-template skill evaluation (FR-007 step 4) is skipped — no AI call is made since there is no career goal to evaluate against.
- **FR-020**: The Roadmap document MUST carry a `personalisationLevel` flag. It MUST be set to `low` when FR-018 applies, and `full` otherwise.
- **FR-021**: Roadmap generation MUST NEVER be blocked or fail due to the absence of career goal data — the low-personalisation pathway is the mandatory fallback.

**Output Storage**

- **FR-022**: On successful generation, the system MUST create a roadmap preview. The preview MUST NOT be committed to the main roadmap collection until the student explicitly accepts it.
- **FR-023**: A student MAY have multiple Roadmap documents in the main roadmap collection. Exactly one roadmap per student MUST be marked primary (`isPrimary: true`) at all times.
- **FR-024**: The Roadmap document MUST include an `acceptedAt` timestamp field. When the student accepts a roadmap preview, `acceptedAt` MUST be set to the acceptance time. A Roadmap document without `acceptedAt` is considered failed/retryable. Transient generation states are not persisted in the main roadmap collection.
- **FR-024a**: The data model MUST include `isPrimary` and enforce one-primary-per-user with a partial unique index on `{ userId: 1, isPrimary: 1 }` filtered by `{ isPrimary: true }`.
- **FR-024b**: The data model MUST include a list/query index supporting roadmap timeline retrieval by `{ userId: 1, acceptedAt: 1, updatedAt: -1 }`.

**Notifications**

- **FR-025**: On successful generation, the system MUST deliver an in-app notification to the student informing them that their roadmap preview is ready for review.
- **FR-026**: If the low-personalisation pathway was used, the success notification MUST include an indication that personalisation quality is limited.
- **FR-027**: On generation failure, the system MUST deliver an in-app error notification to the student. The notification payload MUST include metadata indicating the generation is retryable (e.g., a `retryable: true` flag and a reference to the retry endpoint) so that any consuming surface can present a retry action to the student. The system MUST NOT leave the student without any notification of the failure.

**Retry Mechanism**

- **FR-028**: On generation failure, the system MUST persist a Roadmap document without `acceptedAt` so that the failed/retryable state is readable by any consuming surface.
- **FR-029**: The system MUST allow the student to trigger a retry of a failed generation without requiring profile resubmission. Retryable state MUST be discoverable via 009 contracts.
- **FR-030**: On retry, the system MUST re-read the existing StudentProfile and re-run the full generation lifecycle from the input retrieval step forward.

**Feature Boundaries**

- **FR-032**: Roadmap generation MUST NEVER be blocked by the absence of Feature 003 (Resource Curation) data. The `resources` field on each node is always `[]` after generation — inherited from the template if the template node carries a non-null value, otherwise defaulting to `[]`.
- **FR-033**: Roadmap generation MUST be triggered entirely by internal system events — no student-facing API endpoint for initiating generation is permitted. The acceptance and rejection of a roadmap preview are student actions and MUST be served by dedicated API endpoints that this feature provides.
- **FR-033a**: Feature 009 MUST expose canonical read APIs: `GET /api/roadmaps/primary`, `GET /api/roadmaps/:roadmapId`; and action APIs: `POST /api/roadmaps/primary/accept`, `POST /api/roadmaps/primary/reject`, `POST /api/roadmaps/primary/regenerate`.
- **FR-033b**: Feature 009 MUST expose canonical primary-switch API: `PATCH /api/roadmaps/:roadmapId/primary`.
- **FR-033c**: (Removed — `GET /api/roadmaps/primary` is now the canonical primary-roadmap endpoint; no compatibility alias required.)

**Acceptance / Commit Contract**

- **FR-034**: Upon successful generation, the system MUST provide preview payload for review (notification-driven), but canonical acceptance MUST be payload-based and not depend on server-side preview lookup.
- **FR-035**: The acceptance endpoint MUST receive full roadmap nodes payload from caller.
- **FR-036**: Acceptance MUST execute mandatory server pipeline: (1) filter completed courses, (2) prerequisite validation, (3) commit roadmap document, (4) create `RoadmapProgress` document seeded with all accepted `nodeId` values in `pending` (all other state arrays empty). Step (4) runs after the preview is accepted and the `Roadmap` document is committed — it is a post-acceptance side effect, not part of the commit transaction itself.
- **FR-037**: If all submitted nodes are filtered out as completed, acceptance MUST fail with `ALL_COMPLETED`.
- **FR-038**: If prerequisite or ordering constraints are violated, acceptance MUST fail with `PREREQUISITE_VIOLATION`.
- **FR-038a**: Lifecycle conflicts (e.g., concurrent generation/primary update/duplicate state operation) MUST return `CONFLICT`.
- **FR-039**: When re-generation is triggered, the system MUST check whether the student has an existing accepted Roadmap document. If one exists, the system MUST supply it to the AI as additional context alongside the updated StudentProfile and full CourseUnit DAG. If no accepted Roadmap document exists (e.g., the student previously rejected all previews), the system MUST proceed as a fresh initial generation — StudentProfile and DAG only — without treating the absence of a base roadmap as an error.
- **FR-040**: Feature 009 MUST be the only feature that defines and enforces roadmap state transitions.
- **FR-041**: Acceptance, list/detail/primary, and progress APIs MUST use normalized domain error codes: `PREREQUISITE_VIOLATION`, `ALL_COMPLETED`, `CONFLICT`, `ROADMAP_NOT_FOUND`, `INVALID_TRANSITION`.

**Progress Tracking**

- **FR-042**: On roadmap acceptance (step 4 of FR-036), the system MUST create a `RoadmapProgress` document for the accepted roadmap. The document MUST be seeded with all `nodeId` values from the committed `Roadmap.nodes` placed in the `pending` array; `inProgress`, `completed`, and `skip` MUST all be empty. One progress document per `(userId, roadmapId)` pair is enforced by a unique index. If `createProgress` fails due to a transient error, the system MUST retry at least once before surfacing the failure. If the retry also fails, the Roadmap acceptance MUST still be considered successful (the Roadmap document is already committed); the progress creation failure MUST be logged as a background warning and MUST NOT block or roll back the accepted Roadmap.
- **FR-043**: The system MUST support atomic per-node state transitions on the `RoadmapProgress` document. Each transition MUST atomically pull the `nodeId` from the source state array and push it to the target state array in a single database operation, enforcing the invariant that a `nodeId` exists in exactly one of the four arrays at all times. Valid transitions are: `pending → inProgress`, `pending → skip`, `inProgress → completed`. If the `nodeId` is not found in the declared source state array, the operation MUST fail with `INVALID_TRANSITION`. No reversals are permitted.
- **FR-044**: The system MUST expose a read API (`GET /api/roadmaps/:roadmapId/progress`) and a state-transition API (`PATCH /api/roadmaps/:roadmapId/progress/node`) per contracts/rest-api.md. Both endpoints MUST be auth-scoped to the requesting user.

---

### Non-Functional Requirements

- **NFR-001 (Correctness)**: The node ordering in every generated Roadmap MUST be a valid topological sort of the selected prerequisite subgraph. The system MUST validate the AI's output ordering before storing the document — any ordering violation MUST be treated as a generation failure and MUST NOT be silently stored.
- **NFR-002 (Isolation)**: A generation failure MUST NOT alter the student's StudentProfile or any system state outside the Roadmap document itself.
- **NFR-003 (Idempotency)**: Retrying or re-generating MUST always produce a complete, valid Roadmap document. A partial or corrupted previous document MUST be fully replaced — never merged or appended to.
- **NFR-004 (Extensibility)**: The `resources` field MUST be present in the schema at generation time so that Feature 003 can later populate it without requiring a schema migration or re-generation.
- **NFR-005 (Data Integrity Guard)**: Before beginning topological ordering, the system MUST detect and reject any cyclic dependency in the CourseUnit DAG, storing a descriptive error rather than entering an infinite resolution loop.
- **NFR-006 (Concurrency Safety)**: Only one generation MUST run at a time per student — concurrent duplicate generations for the same student MUST be prevented at the system level.

### Key Entities

- **Roadmap**: A roadmap version document owned by Feature 009. Contains: `userId`, `studentProfileId`, `personalisationLevel`, `isPrimary`, `acceptedAt` (presence indicates acceptance; absence indicates failed/retryable), ordered `RoadmapNode[]`, and timestamps (`createdAt`, `updatedAt`).
- **RoadmapTemplate**: A full low-personalisation roadmap defined as a static JSON file in source code (not a MongoDB collection). Hardcoded by another feature. Feature 009 loads it at generation time, maps the collected deduplicated skills list against it to establish the base node order and node types, and provides the AI only with skills absent from the template for AI-determined insertion positioning and node type assignment.
- **RoadmapPreview**: A transient, in-memory representation for review UX. It is not canonical persistence and not required as acceptance source.
- **RoadmapProgress**: A `roadmap_progress` document owned and managed by Feature 009, fully detached from the `Roadmap` document — no progress fields live on the `Roadmap` schema. Created automatically on roadmap acceptance (seeded with all `nodeId` values in `pending`); state transitions managed by `roadmapProgress.service.updateNodeState`. Tracks per-node progress state using an explicit four-state set-membership model: every `nodeId` in the roadmap lives in exactly one of the four arrays at all times.
  - `pending: String[]` — nodes not yet started; seeded with all `nodeId` values from `Roadmap.nodes` when the document is first created
  - `inProgress: String[]` — nodes the student is currently working on
  - `completed: String[]` — nodes the student has finished
  - `skip: String[]` — nodes the student has explicitly skipped (terminal state alongside `completed`)
  - Moving a node between states is an atomic pull-from-source + push-to-target operation; a `nodeId` MUST appear in exactly one array at any time; no reversals permitted.
- **RoadmapNode**: A single skill entry in the roadmap. Modelled after the roadmap.sh topic/subtopic pattern. Node types:
  - `nodeType: topic` — main-line skill concept, sequentially ordered, foundational to the career goal (`isMainLine: true` equivalent)
  - `nodeType: subtopic` — specific tool or technology that implements a topic skill; links back to its parent topic via `parentNodeId`
  - `nodeId`: Stable identifier for this node (used by Feature 004)
  - `skillName`: The skill or technology this node represents
  - `parentNodeId`: `null` for topics; set to parent topic's `nodeId` for subtopics
  - `relatedCourses`: Array of `{ courseCode, courseName, credits }` objects linking to DAG courses
  - `reason`: Explanation of why this skill is relevant to the student's career goal
  - `resources`: Array of learning resources (enriched by Feature 003)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every student who submits a full profile receives a roadmap whose skill nodes are derived exclusively from career-relevant courses — all required prerequisite courses are represented and only career-targeted electives contribute nodes; no skill nodes derived from extraneous courses appear. Every node carries a non-empty `skillName`, a populated `relatedCourses` array referencing only non-completed selected courses, and a non-empty `reason`.
- **SC-002**: Every generated roadmap's node sequence satisfies all prerequisite constraints — inspecting any pair of nodes (A → B where A is a prerequisite of B) confirms that A appears before B in the sequence, with zero violations across all generated roadmaps.
- **SC-003**: Every student who submits with only a major receives a roadmap whose skill nodes are derived from all required courses of that major, ordered consistently with prerequisite constraints, and flagged as low-personalisation — no student is left without a roadmap due to missing optional profile fields.
- **SC-004**: A student who experiences a generation failure can trigger a retry and receive a fully generated roadmap without resubmitting their profile — the retry path delivers the same output quality as the initial path.
- **SC-005**: Roadmap generation begins within a reasonable time after profile submission, and the student receives an in-app notification upon completion — the student is never left without feedback on generation status.
- **SC-006**: After a student updates their career goal, re-generation produces an updated roadmap that reflects the new goal — the previous roadmap's course selection and skill enrichments are not reused if they conflict with the updated goal.
- **SC-007**: Every node in every generated roadmap contains a non-empty `skillName`, a populated `relatedCourses` reference, and a `resources` field that is always `[]` at generation time — Feature 003 can populate `resources` at any time without requiring re-generation or schema changes.
- **SC-008**: No roadmap generation event causes visible latency or interruption in the student's concurrent use of any other part of the system — generation is fully non-blocking from the student's perspective.

## Assumptions

- The CourseUnit DAG for all relevant majors is fully seeded by Feature 002 before any student submits a profile. If a major has no seeded courses, this is treated as a data integrity issue outside the scope of this feature.
- The in-app notification and SSE delivery infrastructure introduced by Features 001 and 005 is available and operational for this feature to use; this feature does not re-implement the notification mechanism.
- The StudentProfile is immutable after submission (per Feature 001 constraints); the AI always receives a consistent profile snapshot and need not handle mid-generation profile mutations.
- The AI model's outputs may occasionally be invalid or unparseable; the retry mechanism is the designed recovery path for such cases.
- "Asynchronous and non-blocking" means the generation job is enqueued and processed on a background worker; the exact queue implementation is a technical detail outside this specification.
- Feature 004 (Skill Tree) receives the `RoadmapPreview` payload via the generation completion notification and is the surface through which the student reviews and accepts or rejects it. This feature does not constrain the Skill Tree's rendering logic — including any progressive disclosure of node details.

## Out of Scope

- Any frontend or visualisation layer — rendering the roadmap is owned by Feature 004 (Skill Tree)
- Resource curation and population of the `resources` field on roadmap nodes — owned by Feature 003
- Roadmap editing or manual reordering by the student after generation
- Automatic transcript scraping or machine-based course completion detection
- Grade, GPA, or academic performance data in any form
- Admin tooling for reviewing, overriding, or managing individual student roadmaps
- Definition or management of the AI model used for generation (model selection is an operational concern)
- The mechanism by when regenerate is used — that is owned by Feature 005
- Progressive or deferred rendering of skills and supplementary course information (e.g., revealing `skills` on demand rather than upfront) — owned by Feature 004 (Skill Tree)
